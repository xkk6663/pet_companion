## 二、背景与边界

参考范例（STM32H747 双核摄像头终端）里的能力点，按"能不能落到本工程、风险多大"分了三级：

- **P0（现场可靠性，收益最高）**：flash 写静默窗口、启动失败计数 + 安全模式
- **P1（体验与数据完整性）**：AVI 掉电修复、低分辨率 MJPEG 预览、人脸注视联动
- **不做**：USB MSC（用户明确排除）、PPA / LVGL DMA2D / 硬件 JPEG 编码（S31 上编译失败或与硬解争用 2D-DMA，见 `11_遇到的问题.md` F6、`改动记录.md` §7.5/§7.6、§27.1）、OpenAMP（SMP 单固件不需要）、IMU 姿态（无硬件）

约束：**不新增常驻任务、不碰渲染管线、不改分区表**。最终只有 AVI 修复起了一个一次性任务（栈 6144 B，跑完即删）。

## 四、逐项实现说明

### ① flash 写静默窗口（`flash_guard`）

问题：`spi_flash` 擦写会关中断 + 关 cache（PSRAM 与 flash 映射共用 cache），单窗口 94–157 ms。窗口内 RGB 屏 GDMA 读帧缓冲会断流、他核访问 PSRAM 可能 Cache error。

做法：
- `flash_guard_begin(reason)` 取 200 ms 超时互斥锁；
- **录像中 / 收尾中 → 直接返回 `ESP_ERR_INVALID_STATE`**，由调用方延后（绝不打断录像）；
- 取景器开着 → `viewfinder_disable()`；本地音乐在播 → `media_player_service_pause()`；
- `flash_guard_end()` 反向恢复；`flash_guard_is_active()` 供 MJPEG 降速判断。

已包裹的写点：壁纸 `save_last`、Wi-Fi `store_commit`、WS `set_uri`、音乐 `set_cfg`。

### ② 启动失败计数 + 安全模式（`boot_guard`）

- 计数存 **NVS**（`bootg/cnt`）：启动即 +1，走完正常流程 `mark_ready()` 归 0；连续 ≥3 次未归零进安全模式。
- 安全模式只做：`sdcard_service_mount()` → `wifi_manager_init()`（不注册 UI 回调）→ `web_server_init()` → 1 s 延时死循环；跳过相机/音频/模型/录像/UI。
- 出口两个：网页 `POST /api/recovery/clear` + `POST /api/system/reboot`；**或 120 s 内没有"连续稳定 10 s"的 Wi-Fi 连接 → 清计数 + `safe_reboot_perform()` 自愈重启**。

> 关键设计：不能用"某一刻 `wifi_manager_is_connected()`"判连上。实测 STA 关联成功那一瞬也会置位，随后立即 201 断开，会把自愈逻辑骗过去（第一版就是这样卡死在安全模式，见第五节）。

### ③ AVI 掉电修复

`avi_muxer_repair_file(path, &info)`：校验 RIFF/AVI → 定位 `LIST movi` → 从固定偏移 224 顺序扫 `00dc/01dc` 统计帧数、movi 字节数、最大帧、时长 → 遇非视频块（旧 idx1）停止 → 复用 close 的 `patch_headers()` / `write_index_and_sizes()` 回填 RIFF/avih/strh/movi 并重建 idx1。

`record_video_service_repair_start()`：SD 已挂载时起一次性任务（栈 6144、优先级 1、钉 Core0），逐文件修复，日志 `avi repair OK` / `skip`，跑完自删。

### ④ 低分辨率 MJPEG 预览（`/stream.mjpg`）

- 240×240 RGB565 采集 → 双 PSRAM 帧缓冲 + `portMUX` 交换 → `jpeg_util_encode_rgb565_le()` 软编 → multipart 分块发送；
- 单客户端；相机被 MEDIA 占用、录像非 IDLE、或**设备端相机页正占着相机** → 409（手写状态码，IDF 没有 409 枚举）；
- 帧缓冲必须 `heap_caps_aligned_alloc(16, …)`：esp_jpeg 硬性要求输入 16 字节对齐，PSRAM 上普通 malloc 不保证，实测会直接 `ESP_ERR_INVALID_ARG`、`sent=0`；
- 新增诊断：`mjpeg: req owner/running/has_frame_cb`、尺寸不符/编码忙丢帧计数（每 30 次打一条 WARN）、流结束时 `sent / q / ms / fps / drop_size / drop_busy`；
- 支持 `?q=20~90` 调质量（默认 40）：一次烧片就能扫质量-帧率曲线；
- 自己起的流且无 CAM 页回调才 `camera_service_stop()`，退出释放三块 PSRAM。

**实机实测（STA `Power`，IP 10.115.126.252，`/stream.mjpg`）**

| 质量 | 单帧字节 | 帧率 | 单帧软编耗时 |
|---|---|---|---|
| q=70 | 20–25 KB | 1.10 fps | 720–780 ms |
| q=40（默认） | 8.6–12.4 KB | 1.25 fps | 约 750 ms |

结论：**流链路已经通了**（HTTP 200、multipart 正确、浏览器可直接看），但本机软编单帧 ~750 ms 是硬上限，所以帧率只有 1.2 fps——这不是网络问题（RSSI −28 dBm，`root` 页面 0.16 s 返回）。


### ⑤ 人脸注视联动（`tab_camera.c`）

检测到最大脸框 → 目标点 = 框中心 − 9（clamp 到可视区）→ 每 50 ms 用 α=1/4 EMA 平滑 `lv_obj_set_pos`；无脸/检测关闭则隐藏；页销毁置空指针，避免野指针。

## 五、过程中发现并修掉的 8 个真问题

| # | 现象 | 根因 | 处理 |
|---|---|---|---|
| 1 | 编译 `esp_reset_reason.h` 不存在 | IDF v6.1 没有该头 | 改 include `esp_system.h` |
| 2 | `HTTPD_409_CONFLICT` 未声明 | `httpd_err_code_t` 无 409 | 改 `httpd_resp_set_status(req,"409 Conflict")` + `httpd_resp_send` |
| 3 | `snprintf(path…)` 被 `-Werror=format-truncation` 拒 | dirent 名字最长 255，缓冲 128/300 不够 | 扩到 400 B 并注释原因 |
| 4 | **安全模式永远进不去**（实机 fail_count 恒为 1） | 本板每次复位都是 `POWERON`，`RTC_NOINIT` 计数不保留 | 计数改存 **NVS**，跨 panic/WDT/软复位/断电都可靠 |
| 5 | **安全模式进去了出不来**（等 120 s 也不自愈） | STA 关联瞬间 `s_connected=true`，循环立即 break | 改为"连续稳定 10 s"才算连上；补等待日志 |
| 6 | **MJPEG 一帧都发不出**：日志 `mjpeg encode failed: ESP_ERR_INVALID_ARG`、`sent=0` | 帧缓冲用 `heap_caps_malloc` 拿到的 PSRAM 地址不保证 16 字节对齐，esp_jpeg 硬校验直接拒 | 三个缓冲改 `heap_caps_aligned_alloc(16, …)` |
| 7 | **设备相机页开着时网页只连上没画面**（回调全丢，最后 500） | CAM 页以 1280×720 跑帧回调，而流只接受 240×240；且 handler 没判断"相机被 UI 占用" | 加 `has_frame_cb` 判断 → 409 `camera in use by device UI`；回调尺寸不符时计数+WARN |
| 8 | `?q=` 调质量不生效，帧大小始终 24 KB | 把完整 URI 传给 `httpd_query_key_value`（它要的是 query 串，不是 URI） | 改用已有 `query_get(req, "q", …)`（内部先 `httpd_req_get_url_query_str`） |

> 第 4、5 条都是只有上实机才会暴露的问题，纯代码评审发现不了。

## 七、未验证项与已知限制

1. **MJPEG 帧率上限 1.2~1.3 fps**（已知限制，不是 bug）：本机 esp_jpeg 软编 240×240 单帧稳定 750 ms。要更高帧率只有两条路——把预览降到 160×160（约 2.5~3 fps）或 120×120（约 4 fps，画质明显变糊），或换硬编（会和硬解 JPEG 争 2D-DMA，本轮明确不做）。**待你拍板**。
2. **设备相机页与网页预览互斥**：CAM 页开着时网页会拿到 409 `camera in use by device UI`，先退出相机页再开流即可；是否改成"两者共存（降采样第二路）"待定。
3. **客户端断开后最多 60 s 才释放**：手机浏览器直接关页面时，handler 仍在 60 s 上限内继续编码（`s_mj_client` 期间第二个客户端会拿到 400）。想更快释放可以把 60 s 收到 20 s。
4. **注视环**：用户已在设备上目视确认出现；未做录像留证。
5. **AVI 掉电修复的真实掉电样本**：SD 上仍无录像（`/sdcard/videos` 未创建），只验证到"安全跳过"。建议录 10 s → 拔电 → 上电，看 `avi repair OK`。
6. **分区余量 3%**（0x38de0 ≈ 233 KB），后续加功能前要先做体积治理。
7. **安全模式期间无 UI**（屏幕熄灭属预期）。
8. **串口抓日志会复位设备**：`serial_watch.py` 打开 COM9 时 DTR/RTS 拉低 EN，日志里的 `rst:0x1 (POWERON)` 是这么来的，不是掉电或崩溃；抓流验证要与串口抓取错开 20 s 以上。
