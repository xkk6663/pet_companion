# 分层与解耦评估 · pet_companion

> 评估日期：2026-11-20
> 对象：`main/`（app / middleware / ui / 3rd）+ `components/`（vendor）
> 方法：`embedded-mcu-layer-decoupling` 方法论（变化源切层、六层模型、九条解耦律）+ 两套脚本实测
> 结论一句话：**骨架是对的，粒度是错的** —— 三层已经画出来了，但 `middleware/` 是一个 216 条内部引用的强连通耦合团，真正的 L1/L2 两层不存在，于是硬件知识从 40 个文件里各漏一次。

## 0. 摘要

### 0.1 评分卡

| 维度 | 现状证据 | 分 |
|---|---|---|
| 层数与依赖方向 | 有 3 层规范，但存在 20 条反向 include | 5 / 10 |
| 硬件隔离 | UI 15 个文件直接吃 BSP，屏参数被 UI 引用 71 处 | 3 / 10 |
| 接口契约 | 10 个公共头把 `esp_codec_dev` / `bsp` / `esp_cam_sensor` / `esp_mcp_engine` 暴露给消费者 | 5 / 10 |
| 初始化与时序 | `app_main` 36 个编排调用，顺序即依赖，隐式契约写在注释里 | 3 / 10 |
| 配置外置 | 全工程 0 处 `#ifdef BOARD_*` / `MCU_*`，差异靠 Kconfig + BSP 组件 | 9 / 10 |
| 构建期护栏 | CI 只有 pytest；无 include 白名单、无分层检查 | 3 / 10 |
| 可测试性 | 5 个纯逻辑模块能上 host 测（breath_sync / ringbuf / avi / face_quality），服务层不能 | 4 / 10 |
| **加权均值** | | **约 5.0 / 10** |

### 0.2 五个头条数字

1. **`middleware/` 内部 216 条 include 引用、107 个文件、35,359 行**，含一个三方环 `camera ↔ net ↔ media`，以及 `ai↔net`、`ai↔audio`、`net↔periph` 等多组双向对。
2. **换屏 / 换板要改 28 个文件**（app 1 + middleware 12 + ui 15），其中 15 个在 UI 层 —— 这是本工程最贵的一处耦合。
3. **20 条反向依赖**：低层去 include 上层。最典型是 `web_server.c` 一个人 include 了 5 个业务/传输模块，`flash_guard.c` 为了判断"谁在写 flash"反过来 include 了 3 个上层服务。
4. **4 个中间层文件认识 LVGL**：`fs_service.c`、`face_service.cpp`、`screen_shot.c`（还劫持了 `lv_display` 的 flush 回调）、`ai_punch.c`（还建 `lv_canvas` 并调 `ui_binfont_get()`）。
5. **同一套 JPEG 硬件解码能力被写了 5 遍**：`viewfinder.c`、`cloud_media_service.c`、`wallpaper_service.c`、`fs_service.c`、`ai_camera.c`，每处各自 init、各自管理缓冲。

### 0.3 值得保留的资产（不要一起改掉）

- **0 处直接寄存器写、0 处 `#ifdef` 板名、0 处 ISR 里跑业务** —— 硬件耦合停在"头文件级"，没有烂到"寄存器级"，这比多数国产 MCU 工程干净得多，改造成本因此可控。
- **命令队列 + 事件回调模型已经是对的**：`audio_service`（codec 唯一所有者 + ext 租借协议）、`led_service`（UI/MCP 只 post 命令）、`file_mgr_service`、`bt_audio_service` 都是标准的 L3→L4 隔离手法。
- **`breath_sync` 把"亮度 = 绝对 UTC 的纯函数"抽了出来，并进了 host 测试** —— 这正是本工程唯一"真解耦"的样板，方案里就是把这一招复制到别处。
- **运行期护栏完备**：boot_guard 安全模式、flash_guard 静默窗口、`[stack]` 水位报表、内存分步账单 —— 说明架构意识在线，缺的只是"编译期护栏"。

## 1. 审计口径（为什么两个脚本结论不同）

### 1.1 通用脚本 `layer_audit.py` 在本工程的误报

按 skill 默认跑：`404 处 / 120 文件，high=390`。这个数字**不能直接当结论**，原因有三：

| 现象 | 原因 |
|---|---|
| 388 条 `R1 HAL_LEAK` | 规则把 `esp_log.h` / `esp_err.h` / `esp_heap_caps.h` 也算"厂商 HAL"，对 ESP-IDF 属误报；另外 `.workbuddy/ref/` 下还有一份第三方参考工程被一起扫了 |
| `R6 ISR_BLOAT` 14 条 | 全部落在 `.workbuddy/ref/` 的 LVGL 源码里，与本工程无关（本工程 `main/` 下 0 条） |
| `R3 REG_ACCESS` 2 条 | 一条是魔数 `0x42524854`（8 位十六进制，被当成地址），一条是结构体注释 |

剔除平台基础头与 `.workbuddy` 后，`R1` 真实剩余 **94 条**。这 94 条里约 60 条其实是"模块自己就是驱动，因此合理"（`camera_service.c` 引 `esp_video`、`wifi_manager.c` 引 `esp_wifi`、`fs_service.c` 引 `esp_littlefs`）——

> **这恰恰是最有力的证据**：不是规则误报，是这些驱动被放在了名叫 `middleware`（服务层）的目录里。**目录命名本身就是错的**，脚本只是如实反映了它。

剩余约 34 条是真问题：业务层自己抓 HTTP、自己开 FAT 挂载、自己调硬件 JPEG 解码器、UI 层自己去查 littlefs 分区用量。

### 1.2 专用脚本 `tools/layering/layer_guard.py`（本次新增）

按"谁在 include 谁"判层，只盯架构裂缝，不纠结平台头。当前基线：

```
共 55 处 / 37 文件 | high=52 medium=3
规则: G1=20(反向依赖)  G2=16(UI 吃板级头)  G3=10(公共头漏硬件类型)
      G4=6(中间层吃 LVGL/UI)  G5=2(公共头 extern 可变全局)  G6=1(模块环)
```

复现：

```powershell
python tools/layering/layer_guard.py --root . --format text
python tools/layering/layer_guard.py --root . --baseline tools/layering/layering_baseline.json --fail-on high
```

它与通用脚本的分工：**通用脚本管 `R1/R3`（寄存器与 HAL 级），本脚本管 `G1~G6`（层次方向与接口契约）**。两者都要跑，谁也替不了谁。

### 2.2 层间引用矩阵（按 include 次数）

```
middleware -> middleware   216      ← 耦合团本体
ui         -> ui            80
ui         -> middleware    50      ← 合规（向下）
app        -> middleware    29      ← 合规（向下）
app        -> ui             5      ← 合规（向下）
```

`middleware` 子目录之间的引用（≥2 条的）：

```
ai    -> periph 9      ai    -> camera 8     net   -> periph 6
ai    -> audio  5      media -> periph 5     net   -> ai     4
net   -> camera 4      ai    -> net    3     media -> camera 3
net   -> media  3      audio -> ai     2     audio -> bluetooth 2
audio -> periph 2      periph-> camera 2     periph-> net    2
periph-> audio  1      periph-> media  1     ai    -> media  1
```

环：`camera ↔ net ↔ media`（三方）；双向对：`ai ↔ net`、`ai ↔ audio`、`ai ↔ media`、`net ↔ periph`、`audio ↔ periph`。

**这说明 `middleware/` 里同时住着三种东西**：`periph`/`camera_service` 是驱动（L2），`audio`/`net`/`media`/`xiaozhi` 是服务（L3），`ai/*`、`punch`、`wallpaper` 是业务（L4）。三层住一间屋，自然找不到"只能向下"的方向。

### 2.4 UI 层吃 BSP 的真实用量

| 符号 | 层内引用次数 | 说明 |
|---|---|---|
| `BSP_LCD_H_RES` | ui 49 / middleware 3 / app 1 | 屏宽，UI 布局里到处都是 |
| `BSP_LCD_V_RES` | ui 22 / middleware 3 | 屏高 |
| `bsp_display_lock` | ui 5 / middleware 11 / app 1 | LVGL 互斥锁（BSP 提供） |
| `bsp_display_start_with_config` | app 1 | 屏初始化 + task_stack 覆盖 |
| `bsp_i2c_init` | app 2 | I2C 总线 |

结论：UI 对 BSP 的依赖**只有 3 种语义** —— 屏几何、显示锁、亮度/初始化。也就是说，只要一个 3 函数的 port 头就能切断 15 个文件的耦合，**不需要 ops 表，不需要抽象层**。

| 头文件 | 漏出的类型 | 受害者 |
|---|---|---|
| `audio/audio_service.h` | `esp_codec_dev.h` + `bsp/esp-bsp.h` | 4 个消费者（player、xiaozhi、file_mgr、rec） |
| `audio/mic_frontend.h` | `esp_codec_dev.h` | rec / xiaozhi / mic_gate |

## 3. 判定：对九条解耦律逐条打分

| # | 定律 | 现状 | 判定 |
|---|---|---|---|
| 1 | 硬件是数据，不是代码 | 板级信息以 BSP 头形式散落在 28 个文件里；无 `board_map.h` | **缺失** |
| 2 | 接口只有一张函数指针表 | 无 ops 表（单实例直调），这在本工程可接受；但公共头漏硬件类型 | **半数** |
| 3 | 实例 = 只读 cfg + 可变 ctx + 身份 | 全是"静态全局 + `xxx_init()`"单例，cfg/ctx 未分离，句柄为隐式 NULL | **半数** |
| 4 | 注册靠链接器段 | 无；靠 `main.c` 手写调用序列 | **缺失** |
| 5 | 初始化是声明式分级 | 36 行顺序调用；顺序本身是隐式契约（`wifi_manager_set_sys_cb` 必须先于 `init`，注释已说明） | **缺失** |
| 6 | 软开关与硬件存在性分离 | **0 处 `#ifdef BOARD_*`**，差异全在 Kconfig / BSP 组件里 | **达标** |
| 7 | 策略归服务，机制归驱动 | 大体做到（`audio_service` 的 codec 仲裁是全工程最佳实践）；但 `flash_guard` / `safe_reboot` 反向查上层 | **基本达标** |
| 8 | 依赖注入，不用全局查找 | 无注入，全单例直调；好在没有 `get_xxx()` 式名字查找（R4=0） | **缺失** |
| 9 | 扩展靠 API 子类 | 单板单实例，不适用 | **n/a** |

### 3.1 三条根因

1. **按"目录类型"切层，而不是按"变化源"切层。**
   `middleware/` 的定义是"不是 UI 也不是 app 的东西"，于是驱动、服务、业务全进来。skill §1 的口诀是"这次改动理想上只该改几个文件"——现在改一个音频策略要碰 6 个模块，改屏要碰 28 个文件，就是切层切错了的直接后果。

2. **没有"板级语义层"，于是每个模块自己去摸 BSP。**
   UI 要屏宽、壁纸要屏宽、截图要 framebuffer、`page_system` 要分区用量 —— 谁需要谁 include。15 个 UI 文件 + 12 个中间层文件是这么来的，不是有人偷懒，是**没有地方可以找**。

3. **跨层通信没有唯一通道，于是直接 include 对方。**
   时间（3 条）、停机（1 条）、flash 占用（4 条）、HTTP 动作（6 条）、UI 帧（2 条）—— 这五类"横切能力"没有公共入口，每个消费者只能反手抓一个具体模块。

## 4. 目标模型

### 4.1 分层（在现有树内落地，不推倒）

```
main/
├─ app/          L5  启动编排：只调 6 个 stage 函数（本文件从 1,057 行降到 ~300）
├─ business/     L4  业务：ai_action / ai_punch / ai_music / ai_light / ai_speaker / ai_device
│                      punch_service / wallpaper_service / companion_stats
├─ services/     L3  服务：audio_service(仲裁) / xiaozhi(会话) / media_player / ws_client
│                      event_bus / web_server(纯路由) / file_mgr / viewfinder / face 推理
│                      capture / record_video / wifi_manager / net_time
├─ drivers/      L2  驱动：camera(esp_video) / ov3660 / jpeg(codec) / panel / codec(ES8389)
│                      storage(littlefs+sdmmc) / led(RMT) / button / bt
├─ platform/     L1  板级：board_map.h（数据）+ port_display / port_storage / port_time
│                      port_power / port_net
└─ ui/           L6  表现：只 include platform/port_display.h + 各 service 接口头
```

四条依赖铁律（可执行版见第 6 节）：

- 只能向下；向上只走回调 / 事件 / 注册表。
- 跨层只认接口头，不认实现头（`*_ll.h`、`bsp/*`）。
- 同层模块不互相 include 私有头。
- **`bsp/`、`esp_video*`、`esp_lcd*`、`esp_codec_dev*`、`esp_cam_sensor*` 只允许出现在 `drivers/` 与 `platform/`，且每类只允许一个 `.c`。**

### 4.2 每层"做什么 / 不做什么"

| 层 | 做 | 不做 |
|---|---|---|
| platform | 板级常量、引脚、时钟、屏几何、挂载点、时间基准、电源/重启 | 任何策略、任何任务、任何 UI |
| drivers | 一个设备类的机制：打开/读/写/超时；厂商头在此终止 | 重试、分包、协议、状态机 |
| services | 协议、缓冲、调度、仲裁、状态机（audio 的 TTL/租借、ws 的重连退避） | 碰寄存器、碰 LVGL |
| business | 业务规则：打卡判据、点歌流程、灯效语义、工具参数 | 碰硬件句柄、建 LVGL 对象 |
| ui | LVGL 对象与交互 | 建硬件任务、算业务、拿 BSP 常量 |
| app | 顺序与阶段划分 | 业务逻辑 |

### 4.3 现状 → 目标 的层号映射（迁移期同时作为脚本的 `FILE_MAP`）

| 现状路径 | 目标层 | 备注 |
|---|---|---|
| `app/main.c` | L5 | 只留 stage 调用 |
| `middleware/ai/*` | L4 | 但有 1 个例外见下 |
| `middleware/camera/punch_service.*` | L4 | 业务 |
| `middleware/media/wallpaper_service.*` | L4 | 业务（策略：轮换/记忆） |
| `middleware/periph/companion_stats.*` | L4 | 业务（按日分桶） |
| `middleware/face_db/*` | L3 | 存储服务 |
| `middleware/audio/*`、`middleware/net/*` | L3 | |
| `middleware/media/{file_mgr,record_video}` | L3 | |
| `middleware/camera/{viewfinder,face_service,face_recog,capture}` | L3 | 推理与显示消费 |
| `middleware/camera/{camera_service,ov3660_fmt,jpeg_util}` | L2 | 驱动 |
| `middleware/periph/{led,sdcard,fs,button,flash,boot,safe_reboot,breath}` | L2 | 板级机制 |

## 5. 优化方案（5 个阶段，每阶段可编译可回滚）

原则：**先包后拆、一类设备一提交、每步都能 `idf.py build` 通过**。不做大爆炸式重写。

### P0 · 冻结与建基线（0.5 天，零行为风险）

| 动作 | 命令 / 改动 |
|---|---|

### P3 · 抽驱动（2–3 周，一设备类一提交）

顺序按被依赖程度：存储 → 显示/JPEG → 音频 codec → 相机 → LED/按键/蓝牙。

单个设备类的四步（过程中行为不变）：

```
① 写 drivers/drv_xxx.h（只留 init/open/read/write/ioctl + 明确错误码 + 调用上下文说明）
② 写适配实现：内部仍调现有函数（旧路径不删，只包一层）
③ 逐文件替换调用点：只改 include 与函数名，不改控制流
```

三个高价值合并点：

| 合并 | 收益 |
|---|---|
| `drv_jpeg`（enc + dec 单例） | 5 处重复 → 1 处；改解码参数只改一个文件 |
| `drv_http`（客户端 + TLS + 超时/重试策略） | 7 份配置 → 1 份；业务只给 URL 与回调 |
| `drv_camera`（esp_video + ov3660 私有寄存器表） | 唯一允许引用 `esp_cam_sensor/private_include` 的地方（现有注释已论证"引用而非复制"，这条决策保留） |

判据：`G3 = 0`；`grep -r "esp_codec_dev.h" main/middleware` 只剩 `drv_audio.c` 一处；`esp_video*` 只剩 `drv_camera.c`。

## 7. 明确不做（防过度设计）

skill 的"抽象时机规则"：**同一逻辑出现第 3 次、或第二种器件真实落地时才抽象**。本工程据此**主动放弃**以下四项：

| 不做 | 理由 |
|---|---|
| 函数指针 ops 表 + 链接器段注册 | 单板、单实例、无第二实现；`DEVICE_API`/`SYS_INIT` 是 Zephyr 为"多芯片多实例"付的成本，本工程付了收不回 |
| 把 87 个文件搬去重组目录 | 迁移冲突成本 >> 收益；只新增 `platform/`，`drivers/` 按需迁 |
| 动态注册容器（链表/堆） | 内部 RAM 只剩约 4 KB；注册表用固定容量静态数组 |
| 为"换芯片"做抽象 | 真实变化源只有三条：**IDF 升级**、**屏/传感器型号**、**UI 复用到别的板**。只针对这三条抽象 |

也不动 `components/`（vendor）与 `managed_components/` —— 它们的边界已经是对的，`esp_bt_audio` 只出现在 `bluetooth/*`，`hand_detect` 只出现在 `face_service.cpp`。

## 8. 风险点（本工程特有的坑）

1. **屏几何必须留成编译期常量。** `fs_service.c` 用 `BSP_LCD_H_RES * BSP_LCD_V_RES * sizeof(lv_color_t)` 做**分配尺寸**，其它地方也用它做数组维度。换成 `disp_geometry(w,h)` 这类运行期函数会落到热路径、还可能引入 VLA。→ `board_map.h` 里放 `#define BOARD_LCD_H_RES 800`。
2. **初始化顺序不能"顺手优化"。** `wifi_manager_set_sys_cb` 必须先于 `wifi_manager_init`（否则 GOT_IP 事件在回调注册前派发完）、`sdcard_service_mount` 必须在 `bsp_display_start` 之前（内部 RAM 最空、PSRAM 未切碎）、`ui_binfont_load` 必须在建 LVGL 任务之前（flash 读窗口内不能有并发 PSRAM 访问）。P4 只做分组，**不动顺序**。
3. **注册表回调的线程上下文必须写进头文件注释。** 本工程已有多起因"在错误线程碰 LVGL / 阻塞 WS 收包任务"造成的故障（`docs/工程规范/11_遇到的问题.md` F1–F72）。`web_action_register` 的回调在 httpd 任务里跑，`dispnapshot` 的回调在 LVGL 任务里跑，必须逐条标注。
4. **`middleware` 内部 PSRAM/内部 RAM 的分配归属不能因为分层而漂移。** 任务栈一律内部 RAM（F35 教训）；分层只改 include 与函数名，不动 `heap_caps_*` 的 caps 参数。
5. **Windows 下中文路径与编码。** 新脚本输出统一 `utf-8`，跑之前 `$env:PYTHONIOENCODING="utf-8"`；`layer_guard.py` 已按 `utf-8-sig/utf-8/gb18030` 顺序解码源文件。

### D.3 为什么 P3 延后

1. **体积**：bin 距分区上限只剩约 1%（构建已打 nearly full 警告）。合并 3 处 JPEG 硬解码
   为统一 `jpeg_hw_decode_to_rgb888` 需要统一入参/缓冲语义，等于改写运行期解码路径，
   在无实机回归的前提下无法自证等同。
2. **风险**：`drv_audio` 不透明句柄要动 `esp_codec_dev_handle_t`，涉 5 文件 28 处，
   属音频主链路；一旦句柄语义有偏差，症状是「偶发杂音/无声」，静态编译查不出来。
3. **顺序敏感**：解码路径与 `fs_service` 的 768,000 B 缓冲强绑定（缓冲由屏几何宏算出），
   改结构会牵动内存峰值，而内部 RAM 余量约 4 KB。

建议做法：先补 1 条 host 侧 RGB888 输出用例（像素级等同断言），再合并；每次只合 1 处。

### D.4 P4 的实际处理：顺序表冻结

`app_main` 尾段（`disp_start()` 之后到 `boot_guard_mark_ready()`）已逐条核过：
形态是 `init() + MEM_STAGE()` 的纯直线序列，**没有任何 stage 之间的数据依赖**，
但**初始化顺序影响内存峰值**（多处 init 会在内部 RAM 里一次性 malloc 缓冲）。
因此本轮不搬函数，改为把顺序固化成文档 + 代码注释分区，避免未来"顺手调整"：

| stage | 内容 | 关键次序约束 |
|---|---|---|
| S1 显示 | `disp_start()` → MEM_STAGE → `ui_binfont_attach()` → `punch_watermark_ui_init()` → `stack_hwm` 定时器 | 必须先有 LVGL 才能建 timer，且 `punch_watermark_ui_init` 必须在 `ui_binfont_attach` 之后（字体回退依赖） |
| S2 存储与音频 | `fs_service_init` → `audio_service_init` → `mic_monitor_init` → `rec_local_service_init` | `mic_monitor` 依赖 `audio_service` 已建 codec |
| S3 人机 | `led_service_init` → `button_service_init` → `wifi_manager_init` | 按键回调里有 LED 反馈，故 LED 先 |
| S4 媒体 | `camera_service_init` → `file_mgr_init` → `media_player_service_init` | `file_mgr` 依赖 fs；`media_player` 依赖 file_mgr 的目录扫描 |

### E.1 第一次上机：崩了，是本次重构引入的

烧录（`idf.py -p COM9 -b 460800 flash`，写入校验通过）后第一次启动就 panic：

```
Guru Meditation Error: Core 0 panic'ed (Load access fault)
MEPC : 0x40092256   MCAUSE: 5   MTVAL: 0x0a28140a
```

定位过程（全部基于现场数据，不靠猜）：

1. `nm` + 自建符号解析（`0x40092256 -> button_cb+0x58`），栈上返回地址反查得调用链
   `timer_task+0x114 -> button_cb`；
2. 反汇编故障指令：`lw a0, 24(s0)`，`s0 = g_head_handle`（0x2f0448a0）——**供应商
   iot_button 的链表头被写成了野值 0x0a2813f2**；
3. link map 确认该变量在 `.sbss`（vendor 区），不是栈溢出；
4. 时间线锁定：崩溃发生在 `cloud_media_service_init` 之后、`wallpaper_service_init`
   内部（壁纸解码刚开始）；
5. 对照 `git diff`：P1 里我把
   `file_buffer_size = BSP_LCD_H_RES * BSP_LCD_V_RES * sizeof(lv_color_t)` 改成了 `* 2`。
   **LVGL v9 的 `lv_color_t` 是 24 位结构（3 字节）**，而 `esp_jpeg_dec` 输出 RGB888
   也是 3 B/px ⇒ 原值 1,152,000 B 被我缩成 768,000 B，**每解一张壁纸越界写 384,000 B**，
   堆被打烂后任意任务都可能崩（这次落在按键定时器里）。

修复（2 处）：

```c
/* fs_service.c */
file_buffer_size = BOARD_LCD_H_RES * BOARD_LCD_V_RES * 3;   /* 800*480*3 = 1,152,000 B */

/* wallpaper_service.c：上限必须取目标缓冲的真实容量 */
size_t need = (size_t)WP_W * WP_H * 3;
size_t cap  = file_buffer_size;
if (need > cap || (size_t)out_len > cap) { /* 拒绝，不越界 */ }
```

复测：`boot done`、`WP_SVC: decoded 800x480 <- /sdcard/wallpaper/2.jpg`、
PSRAM 余量正好比修复前少 384,000 B（=缓冲增量），确认修复生效。
bin 0x7a4620（分区 0x7c0000，余约 1%）。

### E.4 教训（已写回代码注释）

1. 用 `sizeof(某类型)` 表达缓冲尺寸时，替换成字面常量**必须核对真实 B/px**；
   LVGL v9 的 `lv_color_t` 是 3 字节，不是 RGB565 的 2 字节。
2. 解码/拷贝类 API 的上限检查要对着**目标缓冲的真实容量**，不能对着"理论上够用的假设值"。
3. RISC-V panic 没有 backtrace 时，`nm -n` + 栈上返回地址反查 + 反汇编能定位到指令级；
   这次从 `MTVAL` 的野值定位到 `.sbss` 变量，再靠 link map 找到归属对象。
