## 0. 一句话结论

**架构定稿成立，但"零改动"有两处不成立，开工前必须先按本文件 §2 的裁决修正：**
① HTTP 反向调用需要给 `web_server.c` 新增动作型端点（现有 12 个路由全是只读/查询类）；
② "完全去掉 MCP SDK"与"6 个 ai_*.c 零改动复用"自相矛盾（工具代码全部构建在 `esp_mcp_*` API 上），裁决为**保留 mcp-c-sdk 组件、只删除 vendor 的 MCP 传输使用**。

其余结论全部经源码验证可行，且比架构文档更省：
- **PCM 上行不用另写采集**：av_processor recorder 原生支持 `AV_PROCESSOR_FORMAT_ID_PCM`，把编码格式从 OPUS 切成 PCM 即整条管线复用（含 AFE NS/VAD）；
- **TTS MP3 不用引 minimp3**：av_processor `audio_playback` 的 URL 播放（esp_audio_simple_player 自带 mp3 解码）已在"会话内点歌"链路真机验证，直接复用；
- **WebSocket 客户端不用新拉组件**：`espressif/esp_websocket_client` 已在依赖树（esp_xiaozhi 的传递依赖，`dependencies.lock:512,840`），main 侧声明 REQUIRES 即可。

## 2. 与最终架构文档的差异裁决（开工前必须拍板的 8 条）

### 2.1 ❌ 裁决 1：web_server 不是"零改动"，需要新增动作端点

**现状（已核实）**：`web_server.c` 12 条路由全部只读/查询（打卡是轮询 `/api/punch/last?gen=N`，没有触发端）。架构文档 §1 里"云端插件 HTTP 调 `/api/punch` → 设备执行打卡"目前**不存在**，且 `ai_punch.c` 的 `punch_session()` 是 **static**（`:515`），外部不可调。

**动作**：见 §3.5，新增约 6~8 个动作端点，并为 `ai_punch.c` 加一个公共入口。

**红线**：`esp_http_server` 是**单任务串行**模型（`web_server.c:17-20` 的 §74 铁律：handler 不返回其它请求全部饿死）。打卡是数秒~30 秒长事务，**动作端点必须异步受理**（投队列立即返回 + 代际号轮询结果），照 `on_punch_done` 的 gen+快照槽模式（`:73-89`）。

### 2.2 ❌ 裁决 2：MCP SDK 不能"完全去掉"，改为"保留组件、去掉传输"

**矛盾**：架构文档 D5 建议"完全去掉 esp_mcp_sdk"，但 §3 又承诺 6 个 `ai_*.c`（~2100 行）"零改动复用"。已核实 6 个文件**全部**构建在 `esp_mcp_*` API 上（`esp_mcp_tool_create` / `esp_mcp_add_tool` / `esp_mcp_value_create_*` / `esp_mcp_property_list_t`）。真删 SDK = 6 个文件重写工具层 = 与"零改动"冲突。

**裁决**：
- `mcp-c-sdk` 组件**保留在依赖树**（不删 `dependencies.lock`）；
- 删除的只是 **vendor 对 MCP 的传输使用**（`esp_xiaozhi` 组件随 `xiaozhi_service.c` 改造一并停用，不再有任何 MCP over WS 会话）；
- `ai_*.c` 的 attach 壳层在 P4 阶段二选一（决策 D5'，§7）：**A. 保留 attach（引擎空转，未来可回 MCP）** / **B. 删 attach 壳（省 ~150 行死代码）**。默认 A，保底不误删。

### 2.3 ✅ 修正 3：PCM 上行复用整条 recorder 管线

架构文档 §1 画的是"mic → av_processor recorder → PCM 16k/mono"。已核实 `av_processor` 的 encoder 格式枚举含 `AV_PROCESSOR_FORMAT_ID_PCM`（`av_processor_type.h:49`），`xiaozhi_service.c:842-849` 的 recorder 编码参数从 OPUS 换成 PCM 即可（AFE NS/VAD、16k、单声道全保留）。**不需要**另写采集或解码 Opus。

上行形态：PTT 按住累积 PCM（60ms/块，1920B），松开沿把整段 base64（mbedtls base64）经 WS 上行。单段上限 10s（≈160KB→base64 ~213KB），超长截断（架构 R8）。

### 2.4 ✅ 修正 4：TTS MP3 播放不引 minimp3，复用 playback URL 播放

架构文档 §5.2 写"设备端下载 MP3 → minimp3 解码 → 播放"。已核实 `audio_playback_play(s_play, url)`（`xiaozhi_service.c:957`）走 `esp_audio_simple_player`，HTTP 拉流 + mp3 解码内建，且已在 MCP 点歌链路真机验证。**minimp3 不引**。

两种接法（P3 验证后定）：
- **A（首选）**：新增第二个 `audio_playback` 句柄 `s_tts`（`priority = XZ_TTS_PRIORITY 2`），与 `s_play`（音乐，priority 1）并存——av_processor 音频策略"priority 大者胜出出声"已实证（`xiaozhi_service.c:110-114` 注释），TTS 说话时音乐自动让路、说完恢复。**需验证**：`audio_processor_mixer_open(s_play, s_feeder)`（`:877`）后第二个 playback 是否需进 mixer / 能否直写 play_io。失败则走 B。
- **B（兜底）**：复用 `s_play` 播 TTS——换曲语义是"先停旧流再起新流"（`:950-953` 注释），TTS 会停掉正在播的音乐且不自动恢复，体验降级但零新增句柄。

### 2.5 ✅ 修正 5：`self.camera.explain` 的改造点已定位

已核实 `explain_task`（`ai_camera.c:247-333`）：步骤 1 在 `:257` 现取 vision 端点（`xiaozhi_service_get_vision_endpoint`，该 API 依赖 `esp_xiaozhi_chat_get_vision_endpoint`，换 AstrBot 后失效），步骤 3 在 `:303` 调 `esp_xiaozhi_camera_explain`。

## 3. 设备端逐文件修改方案

### 3.1 新增 `main/middleware/ai/ws_client.c/.h`（~300 行，替代 esp_xiaozhi_websocket.c）

```c
/* ws_client.h —— 接口草案 */
typedef void (*ws_rx_cb_t)(const char *line_json, void *ctx);   /* 逐行 JSON，已按 \n 分割 */

typedef struct {
    const char *uri;          /* wss://<服务器IP>:8080/ws */
    const char *token;        /* 可选 Bearer（自建网关可先空） */
    const char *session_id;   /* xz-s31-<mac末4位> */
    ws_rx_cb_t  rx_cb;
    void       *rx_ctx;
} ws_client_config_t;

esp_err_t ws_client_start(const ws_client_config_t *cfg);   /* 建任务+连接（PSRAM 栈 16KB 照 ai_camera.c:60） */
esp_err_t ws_client_send_text(const char *json);            /* 线程安全，内部加锁 */
bool      ws_client_is_connected(void);
void      ws_client_stop(void);                             /* 断连 + 重连（指数退避 1s→2s→4s→...→30s） */
```

**实现要点（照 `esp_xiaozhi_websocket.c` 已验证模式）**：
- `esp_websocket_client` 事件回调（`WEBSOCKET_EVENT_DATA`）只做两件事：按 `\n` 切行 → 调 `rx_cb`；绝不阻塞、绝不碰 LVGL；
- TLS：`client_config.transport = WEBSOCKET_TRANSPORT_OVER_SSL` + `esp_crt_bundle`（照 `esp_xiaozhi_websocket.c:10` 的用法）；`uri` 走 `wss://`；
- 上行发送：`esp_websocket_client_send_text`（锁保护）；PCM base64 与文字、事件共用同一发送口；
- 重连：`WEBSOCKET_EVENT_DISCONNECTED` 后由 ws 任务指数退避重连；v1 **无状态恢复**（断线丢当前回合，UI 提示"连接恢复"即可，不补发未确认消息——决策 D10）。

**CMake**：`main/CMakeLists.txt` REQUIRES 增加 `esp_websocket_client`、`cjson`（cjson 已在依赖树）。

## 4. 云端网关方案（`ws_gateway.py`，FastAPI，~150 行 + 插件 2 个）

### 4.1 职责与路由

```
GET  /ws/{session_id}              WebSocket 长连接（设备唯一入口）
POST /push                         AstrBot 插件主动推：{session_id, text, emotion, tts?}
POST /health                       存活检查（供设备/前端轮询）
```

### 4.2 上行处理链

| 上行消息 | 网关动作 |
|---|---|
| `{"type":"text","text":...}` | 直接 `POST AstrBot /api/v1/chat`（契约见 4.3） |
| `{"type":"pcm","data":base64,...}` | base64 解码 → 封 WAV 头（44B）→ 百炼 `qwen3-asr-flash`（dashscope API）→ 文字 → AstrBot；失败 → faster-whisper 兜底（P7）→ 再失败 → 下行 `{"type":"error","code":"asr_failed"}` |
| `{"type":"image_req","attachment_id":...}` | 转 AstrBot 消息段 `{"type":"image","attachment_id":...}`（AI explain 共用） |
| `{"type":"event","event":"barge_in"}` | 取消当前排队的 TTS/ASR 任务 |
| `{"type":"event","event":"status",...}` | 记日志/可入 AstrBot 上下文（v1 仅日志） |

### 4.3 AstrBot 调用契约（沿用原移植文档已核实的硬约束）

```python
POST http://127.0.0.1:6185/api/v1/chat
Authorization: Bearer abk_xxx          # chat scope
{"username":"xiao1", "session_id":"xz-s31-<mac末4位>",
 "message":[{"type":"plain","text":"..."}], "enable_streaming": true}   # ★ 必须 JSON true
```

- 正文 = SSE `plain` 增量拼接，`message_saved` + 连接关闭收尾（**无 `complete` 帧**）；
- 回复完整后：调云端已配 TTS → MP3 存静态目录 → 下行 `{"type":"text",...}`（先）+ `{"type":"emotion","name":"speaking"}` → `{"type":"audio","url":...}` → 播完推 `{"type":"emotion","name":"idle"}`（文字先于语音，P4 原则）；
- 命令表：连接建立后首条下行 `{"type":"system","cmd":"command_table","list":[...]}`（插件命令名清单，供设备缓存/展示，架构 R4）。

### 4.4 主动推送（桌宠灵魂）

插件（定时问候/事件提醒）→ `POST /push {session_id,text,emotion}` → 网关查该 session 的 WS 连接 → 下行 text/emotion/audio。**这是长连接存在的原因**（HTTP 做不到云找设备）。

### 4.5 内存纪律（500MB）

- 网关只做转发与编排（~10MB，不含模型）；
- faster-whisper **按需进程**启动（断网/额度尽才拉起来），不常驻；AstrBot 本身 Python 常驻 150~250MB；
- MP3/图片静态目录放磁盘，TTS 文件定时清理（`/tts/*.mp3` 保留 24h）。

## 8. 联调方法论（适配 WebSocket）

| 手段 | 做法 | 能定位什么 |
|---|---|---|
| ① 抓 WS 原始帧 | 网关逐帧打印 `type` + `data[:120]`（日志一行一条） | 是"云端没发"还是"设备没收到" |
| ② 看云端收到什么 | `docker logs astrbot --since 10m \| grep -iE "preview="` | 命令/文字是否被污染（原移植文档 §5.1 教训） |
| ③ 看设备解析结果 | 串口 `[WS]` 逐行日志（cJSON 解析成败 + type） | JSON 字段错 / base64 解码失败 |
| ④ 看设备动作 | 串口 `[XZ_SVC]` / `[WEB]` 日志 | 状态机/端点是否真的执行 |
| ⑤ 端到端验证 | `tools/diag/ws_echo_test.py`（websocat 脚本化）绕过 UI | 网关 ↔ 设备链路是否通 |

**排查顺序图**：
```
设备不说话
  ↓ ① 网关有 WS 连接吗（/health 或连接日志）
  ↓ ② 上行帧到了吗（网关日志 type=pcm/text）
  ↓ ③ ASR/AstrBot 回了吗（网关日志 + docker logs preview=）
  ↓ ④ 下行帧到了吗（设备 [WS] 日志 type=text）
  ↓ ⑤ 气泡/声音出现了吗（[XZ_SVC]/[UI_PET]）
```
