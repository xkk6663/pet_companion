> 状态：**架构定稿，待开发**（2026-10-28）

> 定位升级：从"打卡终端 + 偶尔语音" → **"AI 伴侣大肥鱼的设备端，桌宠伴侣体验"**
> 方法：S9 原方案（HTTPS+SSE）+ Meta Muse Gadgets 架构参考 + 小智协议包袱分析 + 云端全配好现状，四者融合。

## 0. 一句话结论

**放弃 HTTPS+SSE 请求-响应，改走 WebSocket 长连接 + 云端统一网关。**
设备端极简为"屏幕 + 麦克风 + 喇叭"，所有智能（ASR/LLM/TTS/生图/插件）在云端编排。
MCP 工具零改动保留，改为云端 HTTP 反向调用设备 :80 端口。

| 维度 | 原 S9 方案 | 本最终方案 | 为什么改 |
|---|---|---|---|
| 连接模型 | HTTPS + SSE 请求-响应 | **WebSocket 长连接** | 桌宠需要主动推送 + 流式音频，短连接做不到 |
| 设备端入口 | 分散调 3 个 API（AstrBot/TTS/ASR） | **一个 WebSocket 网关** | 云端全配好了，设备端只管收发 JSON |
| 延迟 | ~2.4s（每次 TLS 握手） | **~1.5s**（连接常驻，无握手开销） | 伴侣体验要求首字延迟 < 2s |
| 主动说话 | ❌ 做不到 | ✅ 云端插件主动推 | 桌宠灵魂是"它会先开口" |
| 代码量 | ~600 行客户端 | **~500 行 WebSocket 客户端** | 去掉 SSE 解析/文件下载/附件上传，统一成 JSON |

## 1. 目标架构（最终版）

```
┌─ ESP32-S31 设备（身体，极简）──────────────────────────────┐
│                                                            │
│  [mic] → av_processor recorder → PCM 16k/mono              │
│                                                            │
│  ┌─ ws_client.c（唯一连接，~300 行）───────────────┐       │
│  │  WebSocket ←→ 云端网关（wss://你的IP:8080/ws）     │       │
│  │  上行: PCM / 文字 / 事件（按键/唤醒/状态）           │       │
│  │  下行: 文字 / MP3 URL / 图片 URL / 表情 / 系统指令   │       │
│  └───────────────────────────────────────────────────┘       │
│                     ↕ 事件模型（保留 esp_xiaozhi 事件枚举）    │
│  [session SM] → overlay_pet（桌宠动画 + 对话气泡）            │
│               → feeder(MP3) → [spk]                          │
│                                                            │
│  ┌─ HTTP Server :80（已有，零改动）───────────────────┐       │
│  │  /api/punch /api/media/capture /api/light/* ...    │       │
│  │  ↑ 云端 AstrBot 插件通过 HTTP 反向调用设备工具         │       │
│  └───────────────────────────────────────────────────┘       │
│  /sdcard ← 拍照/录像/云端下发的图（唯一大容量载体）            │
└──────────────────────────────────────────────────────────────┘
                          ↕ WebSocket (wss, TLS)
┌─ 云端服务器（500MB，全配好了）────────────────────────────────┐
│                                                            │
│  ┌─ ws_gateway.py（统一入口，~150 行 FastAPI）─────────┐     │
│  │  设备 PCM → 转发 ASR                                │     │
│  │  设备文字 → 转发 AstrBot /api/v1/chat               │     │
│  │  AstrBot 回复 → 转发 TTS → MP3 URL                  │     │
│  │  TTS MP3 URL → WebSocket 推回设备                    │     │
│  │  主动推送：AstrBot 插件触发 → WS 推给设备            │     │
│  │  生图触发：插件要图 → 调生图 API → 图片 URL 推回      │     │
│  └───────────────────────────────────────────────────┘     │
│                          ↕ 内部 HTTP                        │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐    │
│  │  ASR     │  │ AstrBot  │  │  TTS     │  │  生图    │    │
│  │ qwen3-   │  │ 大肥鱼   │  │ 已配好   │  │ 已配好   │    │
│  │ asr-flash│  │ 17 插件  │  │          │  │          │    │
│  └──────────┘  └──────────┘  └──────────┘  └──────────┘    │
│       ↓ 兜底                                                  │
│  faster-whisper base-int8（~180MB，断网时启用）               │
└──────────────────────────────────────────────────────────────┘
```

**核心设计原则：**
- **P1 设备端零模型** —— 连 ASR 都不跑，所有 AI 在云
- **P2 单一连接** —— 设备端只维护一个 WebSocket，不分散调任何 API
- **P3 会话独立** —— `session_id` = `xz-s31-<mac末4位>`，不复用微信会话
- **P4 文字先于语音** —— 气泡立刻显示，TTS 是增强，失败不影响文字
- **P5 失败要可见** —— 任何错误 LED 闪红 + 日志明确
- **P6 命令不走前缀** —— 插件命令表云端维护，设备端不猜

## 2. WebSocket 消息协议（自定义，极简）

### 2.1 上行（设备 → 云端）

```json
// 语音回合：PTT 录完一段，整段 PCM base64 上传
{"type":"pcm", "data":"<base64 16k/mono/s16 PCM>", "sample_rate":16000, "duration_ms":4200}

// 文字回合（屏幕键盘输入）
{"type":"text", "text":"今天天气怎么样"}

// 事件：按键/状态/唤醒
{"type":"event", "event":"wake"}                           // 未来唤醒词
{"type":"event", "event":"button", "id":"punch"}           // 打卡按钮
{"type":"event", "event":"status", "battery":85, "wifi_rssi":-52}
```

### 2.2 下行（云端 → 设备）

```json
// 文字回复（SSE 流式拼接好的完整句，或分帧）
{"type":"text", "text":"今天东莞多云，26度"}

// TTS 音频（MP3 URL，设备端下载 + minimp3 解码播放）
{"type":"audio", "url":"https://你的服务器/tts/abc123.mp3", "duration_ms":3200}

// 图片（生图或插件图，URL 下载到 /sdcard/cloud_media/）
{"type":"image", "url":"https://你的服务器/img/xyz789.jpg", "caption":"白发斗篷少女"}

// 桌宠表情（驱动 LVGL 动画）
{"type":"emotion", "name":"happy"}    // happy / thinking / listening / speaking / sad / idle

// 系统指令
{"type":"system", "cmd":"reboot"}
{"type":"system", "cmd":"set_volume", "value":60}

// 错误
{"type":"error", "code":"asr_failed", "message":"没听清，请再说一遍"}
```

**协议设计要点：**
- 所有消息一行 JSON，`\n` 分隔，设备端逐行解析
- 音频/图片用 URL，不直接传二进制（省 WebSocket 带宽）
- 表情帧和音频帧配合：收到 `emotion:speaking` → 桌宠开始动嘴；音频播完 → `emotion:idle`
- 没有 `hello`/`goodbye` 握手——WebSocket 连上就是会话，断开就是结束

## 4. MCP 工具保留方案（零改动，架构已验证）

### 4.1 证据链：工具层与传输层本来就没耦合

1. **引擎由调用方注入**：`esp_xiaozhi_chat.h:186`
   ```c
   esp_mcp_t *mcp_engine;        /*!< MCP engine instance provided by the caller */
   bool owns_mcp_engine;         /*!< chat 是否接管其生命周期 */
   ```
2. **工具注册在引擎上，不在会话上**：`xiaozhi_service.c:447-483`
   ```c
   esp_mcp_create(&mcp);
   ai_light_attach(mcp);  ai_speaker_attach(mcp);  ai_camera_attach(mcp);
   ai_punch_attach(mcp);  ai_music_attach(music);  ai_device_attach(mcp);
   ```
3. **六个 `ai_*.c` 文件均不含任何小智协议符号** —— 只依赖 `esp_mcp_engine.h` + 各业务 middleware。

### 4.2 新调用方式：云端 HTTP 反向调设备

原来：云端小智服务器通过 MCP over WebSocket 调设备工具。
现在：**云端 AstrBot 插件直接 HTTP 调设备的 :80 端口。**

```python
# AstrBot 插件示例（Python）
import requests

async def on_punch_command(message):
    # 让 ESP32 设备执行打卡
    r = requests.post("http://<设备IP>/api/punch", timeout=5)
    if r.ok:
        await message.reply(f"打卡成功：{r.json()['name']}")
```

| 对比 | 原 MCP over WebSocket | 新 HTTP 反向调 |
|---|---|---|
| 协议 | MCP initialize + 工具协商 | 直接 HTTP GET/POST |
| 设备端代码 | esp_mcp_transport_http_server | **已有 web_server.c，零改动** |
| 云端代码 | 小智服务器内置 MCP client | AstrBot 插件里写 requests |
| 工具发现 | 自动协商 | 插件硬编码（你自己的设备，你知道有什么） |

**结论：MCP SDK 可以不要了。** 你的设备和你的 AstrBot 都是你自己的，直接 HTTP 调就行。

### 4.3 唯一需要改的：`self.camera.explain`

原 `ai_camera.c` 的 explain 依赖小智 vision endpoint（由小智服务器下发 URL/token）。换 AstrBot 后：

**新方案**：设备拍照 → `POST /api/v1/file` 上传到 AstrBot → 消息段带 `attachment_id` → 让云端 Qwen-VL 来看。
（这正好是 S9 §7.2 的上行发图路径，一举两得。）

## 5. ASR / TTS / 生图选型（保留 S9 分析结论）

### 5.1 ASR：百炼主路径 + faster-whisper 兜底

| 场景 | 用哪个 | 理由 |
|---|---|---|
| 日常 PTT 一句话 | 百炼 `qwen3-asr-flash` | 同步返回、延迟低、36K 秒够用 10 个月 |
| 长录音转写 | 百炼 `qwen-audio-3.1-asr-flash-filetrans` | 1M 秒额度 |
| 流式边说边识别（未来） | 百炼 `qwen-audio-3.1-asr-flash-streaming` | 1M 秒，PTT 模式暂用不上 |
| 断网/额度尽 | faster-whisper base-int8 | ~180MB 内存，中文勉强可用，兜底 |

**降级链：**
```
百炼 qwen3-asr-flash  ── 失败/超时/额度尽 ──→  faster-whisper base-int8
                                                    └─ 再失败 ─→ 云端回 "我没听清，你打字告诉我"
```

### 5.2 TTS：云端已配好，设备端只收 URL

设备端不直接调 TTS API——云端网关收到 AstrBot 回复文字后，内部调 TTS 生成 MP3，把 URL 通过 WebSocket 推给设备。设备端下载 MP3 → minimp3 解码 → 播放。

**好处：**
- 设备端不暴露 TTS API key
- TTS 失败时云端可以降级为纯文字（气泡显示，不播音）
- 未来换 TTS 引擎不用改设备固件

### 5.3 生图：云端已配好，URL 推送

插件要图时，云端网关调生图 API，生成图片存到服务器静态目录，把 URL 通过 WebSocket 推给设备。设备端下载到 `/sdcard/cloud_media/` 并显示。

## 6. 桌宠伴侣体验设计

### 6.1 嘴型同步

```
云端推: {"type":"emotion","name":"speaking"}
    ↓
设备: 桌宠开始动嘴（循环动画）
    ↓
云端推: {"type":"audio","url":"...","duration_ms":3200}
    ↓
设备: 下载 MP3 → 播放（3.2s）
    ↓
播放完毕
    ↓
云端推: {"type":"emotion","name":"idle"}
    ↓
设备: 桌宠停止动嘴
```

不需要逐帧嘴型同步——表情状态机 + MP3 播放时长，用户感知已经足够。

### 6.2 主动说话（桌宠灵魂）

AstrBot 插件（比如"定时问候"插件）触发时：
1. 插件生成文字 + 表情
2. 调云端网关的内部 API：`POST /push {session_id, text, emotion}`
3. 网关通过 WebSocket 把消息推给设备
4. 设备气泡弹出 + 桌宠切换表情 + TTS 播放

**这就是为什么必须长连接**——HTTP 请求-响应做不到"云端主动找设备"。

> **Meta 参考**：`musegadget send-user-msg "车库门开了一小时了"` —— Linux SDK 里设备端一个普通进程就能往云端 agent 推消息，云端正常回复后再推回设备。你的网关 `POST /push` 就是这个模式，桌宠的"大肥鱼先开口"完全照抄这个设计。

### 6.3 打断（barge-in）

用户说话时设备正在播音：
1. 用户按 PTT 键
2. 设备立刻停掉 feeder（音频播放）
3. WebSocket 发 `{"type":"event","event":"barge_in"}`
4. 云端网关取消正在排队的 TTS
5. 设备开始录音

这个比小智简单——没有回合状态机，就是"停播 + 开始录"。

> **Meta 参考**：`musegadget voice-call --live` 默认**半双工**——播音时自动门控麦克风（防回声），用户开口立刻 `barge_in()` 打断。`--full-duplex` 关掉回声保护（要自己戴耳机或做 AEC）。参数：`--mic-threshold 500`（RMS 静音门限）、`--idle-timeout 45s`、`--overall-timeout 300s`。未来做唤醒词时这套门控逻辑直接抄。

## 8. 风险登记表

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | 服务器 500MB 跑 WebSocket 网关 + AstrBot + 兜底 ASR | 内存 OOM | 网关只做转发（~10MB）；faster-whisper 按需启动，不常驻 |
| R2 | WebSocket 长连接掉线 | 设备变成哑巴 | 自动重连（指数退避，1s→2s→4s→...→30s）；重连后补发未确认消息 |
| R3 | TLS 握手内存峰值 | 设备 PSRAM 紧张 | 照抄 `ai_camera.c` 的 PSRAM 栈模式（16KB PSRAM 栈） |
| R4 | 插件命令表不同步 | 新插件命令掉进闲聊 | 命令表云端维护，启动时 WebSocket 首条消息下发给设备缓存 |
| R5 | 8080 端口现有服务冲突 | 网关起不来 | P0 先 `netstat -tlnp` 确认 8080 占用，必要时换端口 |
| R6 | TTS MP3 下载失败 | 有文字没声音 | 降级为纯文字气泡，日志记 `tts_download_failed` |
| R7 | barge-in 时音频缓冲未清 | 尾音残留 | PTT 按下时立刻 `feeder_stop()` + 清 ringbuf |
| R8 | WebSocket 消息太大（PCM base64） | 带宽/内存压力 | PCM 单段不超过 10 秒（160KB base64 ~213KB），超过截断 |

| D4 | TTS 引擎 | 云端已配好的 / 重新选 | **用已配好的**，设备端不关心是 CosyVoice 还是什么 |

| D6 | 会话 ID | `xz-s31-<mac末4位>` / 复用微信 | **设备独立**，不和微信混 |
| D7 | 桌宠动画素材 | LVGL 矢量绘制 / GIF 帧 | **LVGL 矢量**——省 Flash，好改表情 |

## 10. 与 S9 原方案的关键差异总结

| 维度 | S9 原方案（HTTPS+SSE） | 本最终方案（WebSocket） |
|---|---|---|
| 定位 | 打卡终端 + 偶尔语音 | AI 伴侣桌宠 |
| 连接 | 短连接，每次 TLS 握手 | 长连接，握手一次 |
| 延迟 | ~2.4s | ~1.5s |
| 主动推送 | ❌ | ✅ |
| 代码量 | ~600 行客户端 | ~600 行客户端（网关在云端，设备端更轻） |
| MCP | 保留 esp_mcp_sdk | 去掉 SDK，HTTP 反向调 |
| 音频上行 | PCM POST 整段 | PCM WebSocket 二进制帧（未来可流式） |
| 音频下行 | SSE 传文本 → 设备调 TTS API | 云端网关 → MP3 URL → 设备下载播放 |
| 灵感来源 | 小智协议迁移 | Meta Muse Gadgets（哑终端 + 一个 token） |

**一句话**：Meta 说的"核心是一个 API token"，在你这里就是"核心是一个 WebSocket 连接"。设备端不需要知道有多少 API、有多少插件、有多少模型——它只需要知道：连上那个网关，收消息，显示，播音。所有智能在云端。

### Linux SDK 扩展方式（可直接借鉴）

```bash
# 加新命令：改 src/musegadget/executor.py 的 COMMAND_SPECS
# 主动推消息：
musegadget send-user-msg "车库门开了一小时"
musegadget send-user-msg --session-id <uuid> "发到侧边聊"
# 语音通话：
musegadget voice-call --vm-id XXX --live          # 实时麦克风

```

**对你的启示**：
1. **设备主动推消息**这个模式是桌宠灵魂——你的网关 `POST /push` API 一定要做，AstrBot 的定时问候插件直接调它。
2. **半双工门控**未来做唤醒词时参考——播音时静音麦，开口立刻打断，不用自己从头设计回声逻辑。
3. **工具声明式注册**（`COMMAND_SPECS`）比 MCP 协商轻得多——你的 6 个 `ai_*.c` 已经是这个思路了，继续保持。
