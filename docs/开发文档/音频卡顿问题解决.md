## 0. 先把「缓冲为什么回到 20 KB」说清楚

### 0.1 这不是「把缓冲调小」，是**撤销一个组件源码补丁**

时间线（全部可查 `改动记录.md`）：

| 时刻 | 事件 | 当时的 `HTTP_STREAM_RINGBUFFER_SIZE` |
|---|---|---|
| 2026-11-10 用户贴日志 | 三段 TTS `maxgap = 824 / 1842 / 1441 ms`，`stalls = 16~30`（§26.1） | 官方默认 **20 KB**（这些卡顿数据就是在 20 KB 状态下测出来的） |
| §26 | 把 `esp_gmf_io_http.h` 里的宏**直接改成 128 KB** | 源码里变成 128 KB，**但用户从未烧过这一版** |
| §27 | 又改了 `esp_gmf_rate_cvt.c` 的 bypass 行为（后被证明归因有误，§29.4） | 同上 |
| §29（用户选方案 B） | 两个托管组件一起**回退到组件管理器缓存的官方原版** | 回到官方 **20 KB** |

⇒ 所以「20 KB 缓冲回来了」**不是新决策，也不是为了优化而调小**，是把被 `.gitignore` 忽略的 `managed_components/` 恢复成官方原样。

### 0.2 会卡吗？—— 会，而且和之前那批日志一样卡

上一轮我说「`maxgap 1.2~1.8 s` **可能回升**」，这句话其实**说轻了，而且措辞不准**：

- 那组 `maxgap` 本来就是在 **20 KB** 状态下测出来的，回退后不是「回升」，是**回到原来那个卡的基线**；
- §26 的 128 KB 是当时**唯一直接针对上游断供的缓解措施**，随回退一起撤销了，而 §29 只做了「回退 + 守采样率契约」，**没有补上任何替代缓解**；
- 因此当前工作区编译烧出来的固件，TTS 播放体验应当与 §26.1 那三段日志**基本相同**（墙钟约为音频时长的 2 倍，一帧一帧）。

一句话：**回退解决了「代码不可追溯」的问题，没有解决「声音卡」的问题。**

### 0.2b 2026-11-11 补测：这不是「缓冲不够」，是「供给不足」

| 量 | 值 |
|---|---|
| TTS 源格式 | 24 kHz / 1ch / 16 bit = **48 KB/s** |
| 设备侧实测下行 | 444,912 B ÷ 18.0 s = **24.7 KB/s** |
| PC 直连同一 URL | 2,316,102 B ÷ 16.3 s = **142 KB/s** |
| play_io 消耗 | 16000×2×2 = **64 KB/s** |

设备下行只有 PC 的 **1/6**，而且**低于源码率**。缓冲再大也只是把「多久卡一次」拉长，
消不掉每秒 24 KB 的缺口 ⇒ 优先级从「加缓冲」改成「先把链路吞吐拉回来」（§4 M0）。

### 0.3 为什么当时撤销

不是因为「128 KB 无效」，而是因为它落在了项目明令不改的地方：

1. `managed_components/` 被 `.gitignore:7` 忽略 ⇒ 补丁不随 git 走，换机 / `idf.py reconfigure` 重拉组件即静默丢失；
2. `改动记录.md` §73.27 补充 4 修订（`:6115~6140`）原文写明「**正解 = 纯 sdkconfig 配置，零组件改动**」「managed_components 恢复零改动状态，从此无重装重打负担」；
3. 同一个补丁包里还捆绑了 §27 那个**归因错误**的 `rate_cvt` 改动，两者一起烧无法归因。

### 0.4 上一轮处理得不够好的地方（需要承认）

**更合理的做法是「只撤错误归因的 §27 补丁，保留并正规化 §26 的缓解」**：§26 的机理（20 KB ≈ 0.3 s 缓冲挡不住 1.8 s 空窗）有实测数据支撑，且 128 KB 落在 PSRAM、不吃紧张的内部 RAM。上一轮为了「守纪律」把两个补丁一刀切撤掉，导致用户体验零改善，只留下基线。

★ **但 2026-11-11 补测后，本节原推荐的 S1（整段预取到 SD）已撤回**，理由见 §4.0：
用户提出的两条质疑（SD 累积、首播变慢）都成立，且在 24.7 KB/s 下首播要 ~70 s。

## 1. 音频链路采样规则（铁律，改格式前必读）

### 1.1 一条铁律

> **慢放 ⇔「数据格式 ≠ 流声明格式」，与采样率数值本身无关。**
> —— `改动记录.md` §73.27 补充 7（`:6266~6292`）、`todolist.md:384`。

`esp_ae_rate_cvt` 是正规重采样器，48 kHz 真机也能正常播；历史上「2 倍 / 6 倍慢放」是因为当时 `RESAMPLE_DEST_RATE=48000` + `CH_CVT_EN=n`，48k/2ch 的 PCM 被塞进声明 16k/1ch 的 mixer，数据量差 6 倍。**所以不要靠「猜采样率」修音频问题。**

### 1.2 16k / 2ch 静态锚点与「三方一致」

单 I2S 控制器共享时钟，DAC 同一时刻只能有一个格式；动态切钟会导致 codec 反复 reopen、mic 格式漂移、barge-in 竞态 ⇒ 用户已拍板定档 **16000 Hz / 2ch / 16 bit**（§73.27 补充 7）。

必须恒等的三方：

```
ASP 输出（Kconfig 决定）  ≡  play_io 声明  ≡  mixer / codec open 声明
   16000 / 2 / 16             16000 / 2 / 16        16000 / 2 / 16
```

证据：`xiaozhi_service.c:72-76`（`XZ_PLAY_RATE=16000` / `XZ_PLAY_CHANNELS=2`）、`:684-687`（`audio_manager_config_set_play_io_format`）、`:690-700`（spk / mic 都按 16k/2ch open，**物理时钟对齐 TX**）。

### 1.3 四项不可单改的 `sdkconfig` 契约

`sdkconfig:5258-5261` 与 `sdkconfig.defaults:314-317` 同值（改一处不改另一处，`fullclean` 后会被打回）：

| 配置 | 值 | 作用 |
|---|---|---|
| `CONFIG_ESP_AUDIO_SIMPLE_PLAYER_RESAMPLE_EN` | `y` | 编译进 `aud_rate_cvt`，网关 24k → 16k 的**真重采样** |
| `CONFIG_AUDIO_SIMPLE_PLAYER_RESAMPLE_DEST_RATE` | `16000` | 必须与 `play_io` 一致 |
| `CONFIG_ESP_AUDIO_SIMPLE_PLAYER_CH_CVT_EN` | `y` | 编译进 `aud_ch_cvt`，TTS 单声道 → 2ch |
| `CONFIG_AUDIO_SIMPLE_PLAYER_CH_CVT_DEST` | `2` | 必须与 `play_io` 一致 |

★ **网关 TTS 源是 24000 Hz / 单声道 WAV**（`S9_云端网关_开发文档.md:151, 317, 321`：`"format":"wav","sample_rate":24000`，`normalize_wav()` 只修长度占位、**不改采样率**）。所以 `rate_cvt` 是 24k→16k 的真重采样，不是「ratio=1 白跑」。**关掉 `RESAMPLE_EN` 会立刻重踩慢放坑**（§29.3）。

### 1.4 三条禁止动作

| 禁止 | 原因 |
|---|---|
| 关 `RESAMPLE_EN` / 改 `DEST_RATE` / 改 `CH_CVT_DEST` | 破坏三方一致 ⇒ 慢放。若确需关，**必须先在网关把 TTS 输出改成 16000/2ch**，再设备端关，同批复验语速 |
| 把播放任务优先级提到 **> 10** | `esp_gmf_io_http.h` 的 `HTTP_STREAM_TASK_PRIO = 10` 是**生产者**，播放任务（7）是消费者；消费者更高会饿死拉流任务，更卡（§26.2） |
| 直接编辑 `managed_components/` | 被 gitignore、reconfigure 即还原、升级即冲突、diff 无处可查 |

### 1.5 为什么本地 MP3 用 44100 不违反锚点

本地音乐走**独立管线** `media_player_service.c` → `esp_player`(GMF)，`MP_OUT_FMT = 44100/2ch/16bit`（`:103-105`），经 `audio_service_ext_claim()` 独占 codec 并按该 fmt 重新 `esp_codec_dev_open()`（`audio_service.c:137-169`）。它与小智会话通过 **ext 槽位互斥**（`ext_slot_busy_locked()`），**同一时刻只有一种格式在 I2S 上**，所以不冲突。§73.27 补充 7 原文亦写明「本地 MP3 走独立管线，不受影响」。

## 2. 当前音频链路采样现状（2026-11-11 工作区）

### 2.1 下行 TTS / 点歌 URL（ASP 管线）

```
网关 /static/tts_*.wav  (24 kHz / 1ch / 16bit WAV；样例 1.79 MB，实测段 218 KB / 445 KB)
        │  HTTP GET，边下边播
        ▼
io_http         core 0 / prio 10 / ringbuffer 20 KB / io_size 3 KB   [esp_gmf_io_http.h:16-20]
        ▼
aud_dec (WAV/MP3)
        ▼
aud_rate_cvt    24k → 16k        [CONFIG_..._RESAMPLE_EN=y, DEST_RATE=16000]
        ▼
aud_ch_cvt      1ch → 2ch        [CONFIG_..._CH_CVT_EN=y, DEST=2]
        ▼
play_io         16000 / 2ch / 16bit = 64000 B/s   [xiaozhi_service.c:684]
        ▼
xz_play_write_cb → esp_codec_dev_write(spk) → I2S TX   [xiaozhi_service.c:263-295]
```

- 元素表是**条件插入**：`esp_audio_simple_player.c:45-49` 的 `el_names[]` 由 `#ifdef CONFIG_...` 决定（§29.3 已更正 §27 的「无条件插入」误判）。
- 一个 ASP work task **串行**完成「拉流 + 解码 + 重采样 + 写 I2S」（§21.3 表），`XZ_PLAY_TASK_PRIO=7 / CORE=1`（`xiaozhi_service.c:114-115`）。
- HTTP IO 的默认 `buffer_size` 在 `audio_simple_player_pool.c:21-26` 由 `HTTP_STREAM_CFG_DEFAULT()` 在**组件内部**构造。

### 2.2 本地 MP3（独立管线）

```
SD 文件 → esp_player(GMF) → [rate_cvt 仅 src≠44100 时创建] → 44100/2ch/16bit
        → audio_service_ext_write() → codec（ext 占有，44100/2ch）
```

`media_player_service.c:180-195` 把 `rate_cvt` 的 `src_rate/dest_rate` 显式对齐 44100、`complexity=1`；官方 `audio_render_optimize_pipeline()` 在 `src==dest` 且每秒字节数相等时**不创建**该元素（§29.4 ②）。开关 `CONFIG_PET_MP_RATE_CVT_ENABLE=y`（`main/Kconfig.projbuild`，A/B 用）。

### 2.3 上行（会话期常驻）

```
mic（按 16k/2ch open，物理时钟对齐 TX） → mic_frontend(MONO) 只取 L → 16k/1ch
        → ai_afe → aud_rate_cvt → aud_ch_cvt → aud_bit_cvt → aud_enc → WS
```

- `audio_processor.c:1311-1314` 的 AFE/PCM recorder pipeline **固定包含 `aud_rate_cvt`**（G711/PCM/AAC 三档都有；仅 OPUS 档没有），这一条不受 ASP 的任何 Kconfig 控制。
- `audio_processor.h:478/489` 提供 `audio_recorder_pause/resume`。

### 2.4 会话期任务与优先级（§21.3 表，来自各文件真实宏）

| 任务 | prio | 核 | 备注 |
|---|---|---|---|
| `recorder_task` | **10** | 1 | 上行，固定含 `aud_rate_cvt` |
| `io_http` 拉流 | **10** | **0** | 生产者，别抢它 |
| WS 收包 | 8 | — | `ws_client.c` |
| ASP 播放 | 7 | 1 | §21 从 4 提到 7，仍卡 |
| AFE feed / fetch、uplink、music | 5 | 1 | `cmedia` 图片解码 4 |
| `CONFIG_ESP_TASK_WDT_TIMEOUT_S` | 5 s | — | `sdkconfig:3176`，CPU0/CPU1 IDLE 都在监控内 |

### 2.5 关键换算（后面判据要用）

| 量 | 值 |
|---|---|
| play_io 数据率 | 16000 × 2 × 2 = **64000 B/s** |
| 官方 ringbuffer 20 KB | 20480 / 64000 ≈ **0.32 s** 音频 |
| §26 曾改的 128 KB | 131072 / 64000 ≈ **2.05 s**（刚好覆盖实测最大 1.842 s 空窗） |
| 实测单块写入 | ≈512 B ≈ 8 ms，`writes` 421~869 次（§26.1） |

## 3. 卡顿根因（分层，标明证据强度）

### 3.1 R1 · 上游断供 / 边下边播缓冲见底 —— **已证实**

| 证据 | 值 |
|---|---|
| §26.1 段 1 | 218,296 B，墙钟 8.2 s，`audio` 4.55 s，`stalls=16`，`maxgap=824 ms` |
| §26.1 段 2 | 444,912 B，墙钟 **18.0 s**，`audio` **9.27 s**，`stalls=30`，`maxgap=**1842 ms**` |
| §26.1 段 3 / 另一版 | `maxgap=1441 ms` / `maxgap=1200 ms, stalls=15` |
| `audio` 秒数与数据量吻合 | **一字节没丢**，不是 policy 丢帧、不是解码慢；一半墙钟在空等 |
| `ESP_GMF_HTTP: No more data` 出现在 FINISHED 前 100~200 ms | 播放器一直追着下载进度在播 |

⇒ 0.32 s 的缓冲挡不住 1.8 s 的空窗，网络 / 图片下载 / 日志任一抖动都会直接变成 I2S TX 欠载。**这是「云端对话卡、本地 MP3 不卡」的主因**（本地 MP3 是 SD 文件，无网络环节，§21.3 表）。

### 3.2 R2 · CPU1 被长期占用（`task_wdt`）—— **现象确证，调用方未定位**

用户 2026-11-11 日志（播放本地音乐 `music=1 tts=0` 时）：

- `task_wdt` 在 102472 / 107472 连报两次，间隔正好 5000 ms，`IDLE1 (CPU 1)` 喂不上狗；
- PC / 栈落在 `fa_resample_process`（`rsp_proc.c.obj`，属 `esp_audio_effects` 的 `lib/esp32s31/libesp_audio_effects.a`）；
- MEPC / RA / SP 两次相同，但 **A0/A1/S1/S6…不同** ⇒ 同一函数被**持续占用 / 反复执行**，不是一条指令死循环；
- 同期 `rec read gap 154 / 120 ms > 47 ms`、`uplink xrun=1→3` ⇒ 上行同步断供。

**强假设（未证实）**：占核的更可能是**上行 recorder_task（prio 10, core 1）里的 `aud_rate_cvt`**（§2.3），而非播放链路 —— 因为 `tts=0` 时照样报，且 recorder 优先级高于 ASP 播放任务。§29.4 已把 §27 的「本地音乐 ratio=1 白跑重采样」归因推翻。

★ **不要**把「CPU 抢占造不出秒级空窗」当成排除 R2 的理由：那只对毫秒级调度成立，死循环 / 长期占核可以造出秒级断供（§27 已订正 §26.2）。

### 3.3 R3 · 并发干扰 —— **已部分缓解**

| 干扰 | 现状 |
|---|---|
| 云端「先图片后 TTS」，图片下载/解码与起播重叠 | 网关已做 align8 + 小图（§23/§26），但下载仍与起播抢 PSRAM 带宽 |
| `MIC_FE: diag` 每 5 s 在 AFE feed 上下文做浮点统计 + UART 日志 | §26 已有 `mic_fe_set_diag_hold(true/false)`，TTS PLAYING 期间挂起；**只影响诊断，AFE 数据不变** |
| AFE 全双工，mic 收到喇叭回声 | `L_rms` 200~900；回声也会污染 corr，但不直接造成下行欠载 |

### 3.4 R4 · 慢放坑 —— **已解决，但最容易被「优化建议」带回来**

历史问题（§73.27 补充 4/7），不是当前卡顿。任何「关 `RESAMPLE_EN`」「把 TTS 直接按 24k 播」「动态切采样率」的建议都会立即复现。**当前语速 / 音调正常 ⇒ R4 未激活。**

### 3.5 明确排除

| 排除项 | 依据 |
|---|---|
| 播放任务优先级太低 | prio 4→7 已生效仍卡（§26.1） |
| 音频 policy 丢帧 / 解码慢 | `audio` 秒数与 HTTP 字节数吻合 |
| 采样率不匹配 | 语速 / 音调正常，四项契约同值 |
| 云端生图 jpeg 尺寸报错 | 已 align8，本轮日志 `published 272x272` 且无 decoder 报错 |
| §27 的「官方 bypass 仍调 process 是元凶」 | 本地音乐 src==dest 时根本不创建该元素（§29.4 ②） |

## 4. 可执行解决方案

> 排序原则：**先拿可归因的基线，再上零组件改动的缓解，最后才考虑动组件 / 网关。**
> 每个方案都标了改动范围。★ 2026-11-11 更新：**M0 已落地**（只改 `sdkconfig`），其余仍待授权。

### 4.0 结论重排（2026-11-11）：先治「供给」，不治「缓冲」

| 序 | 方案 | 代价 | 状态 |
|---|---|---|---|
| **M0** | **`ESP_WIFI_RX_BA_WIN` 2 → 16** | 改 1 个 sdkconfig 项 | ★ **已改，待烧录验证** |
| M1 | 网关 TTS 改 MP3（24k mono / 48 kbps，字节 ↓8×） | 云服务器一处参数 | 待办（用户暂不动网关） |
| M2 | ringbuffer 20 KB → 128 KB（受控 fork） | 改 `idf_component.yml` ⇒ **整表重解析** | **暂缓**，见下 |
| S1 | 整段预取到 SD | 首播 70 s + SD 累积 | ❌ **撤回** |
| S2 | TTS 期间暂停上行 | 影响 barge-in | 保留（针对 R2） |
| S5 | `task_wdt` 定位 | 需 A/B 烧录 | 保留 |

**M2 为什么暂缓**：`idf_component.yml` 里写死了 `manifest_hash`，加一条 `override_path` 会触发
全表重解析，实测把 **17 个组件升了版**（button 4.2.1→4.2.3、dl_fft 0.7→0.8 …）。本工程对下载源
敏感（.cn 镜像 403），升级要重下 + 重新验行为。M0 若把下行拉到 ≥48 KB/s，20 KB 缓冲就够用，
不必付这个代价。详见 `改动记录.md` §30.4 / §30.5。

### S0 · 零改动基线（前置，必须先做）

1. `idf.py reconfigure` → `idf.py build` → 烧录。★ 新增过 `main/Kconfig.projbuild`，跳过 reconfigure 会让 `CONFIG_PET_MP_RATE_CVT_ENABLE` 缺失，静默编译成 OFF（验收清单 J0'）。
2. 开机确认 `MP_SVC: gmf pool: rate_cvt=ON dest=44100 complexity=1`；`HTTP_STREAM_RINGBUFFER_SIZE` 为 `(20 * 1024)`；`esp_gmf_rate_cvt.c` 含官方 `This case rate conversion is do bypass`、无 `§27` 字样。
3. 连续播 3~5 分钟 + 一次云端对话，记录三行：`tts stat: ... stalls/maxgap/wr_max/wr_slow`、`task_wdt ... IDLE1` 次数、`uplink ... xrun=`。
4. **烧录前先关上位机**（周期心跳会把一次性崩溃放大成崩溃循环）。

⇒ 没有这份基线，后面每个 A/B 都无法归因。

### M0 ·【已落地】`ESP_WIFI_RX_BA_WIN` 2 → 16（只改配置）

```diff
- CONFIG_ESP_WIFI_RX_BA_WIN=2      # sdkconfig:3270（range 下限的陈旧遗留值）
+ CONFIG_ESP_WIFI_RX_BA_WIN=16     # sdkconfig + sdkconfig.defaults 双写
```

依据：IDF v6.1 `esp_wifi/Kconfig:199-212` 写明 `SPIRAM_TRY_ALLOCATE_WIFI_LWIP=y` 时
**default 与最小值都应是 16**；本工程正是该组合，却停在 2（聚合窗口只 2 帧）。

判据：烧录后同一段对话，`tts stat` 的墙钟 ÷ `audio` 秒数应从 **~2.0 降到 ≤1.2**、
`maxgap` 从秒级降到百毫秒级 ⇒ 说明下行已追上源码率 48 KB/s。
若 `maxgap` 仍 >1 s 且 `wr_max`（写 codec 耗时）很小 ⇒ 吞吐没救回来，转 M2 / 查 RSSI。

### S1 ·【已撤回】整段预取 → SD + file IO

> ❌ **不要做**。撤回依据（2026-11-11）：
> ① 1.79 MB 样例按实测 24.7 KB/s 需要 **~70 s** 才开口，语音助手不可接受；
> ② SD 累积只能靠「单文件名覆盖 + 开机清理」压住，且每轮 TTS 写 0.2~1.8 MB，
>   一天上百轮 = 数十 GB 擦写，为一个缓冲磨卡不划算；
> ③ 它假设「下载比播放快」，而实测正好相反 —— 前提不成立。
> 保留原文仅供追溯，**实施步骤已作废**。

### S2 ·【推荐】TTS 期间降载（**零组件改动，针对 R2 / R3**）

| 动作 | 位置 | 风险 |
|---|---|---|
| TTS `PLAYING` 时 `audio_recorder_pause()`，`FINISHED/STOPPED` 时 `resume()` | `audio_processor.h:478/489`；挂在 `xiaozhi_service.c` 现有 TTS 状态回调里（已在该处调 `mic_fe_set_diag_hold`） | ★ **会让 barge-in（说话打断）失效**；需保留 echo guard 200 ms，或只在「TTS 稳定播放期」暂停、首尾各留 200~300 ms 采集窗口 |
| TTS 期间挂起云端图片下载 / JPEG 解码 | `cloud_media_service` 队列 | 图片显示延后，可接受 |
| 保留 `mic_fe_set_diag_hold(true/false)` | §26 已落地 | 零风险 |

A/B 判据：同一段 TTS，对比「暂停上行」前后 `task_wdt ... IDLE1` 次数与 `uplink xrun`；两者都降 ⇒ 坐实 R2 在上行链路。

### S3 · 若**必须**加大 HTTP 缓冲：正规落地路径（不要再改 `managed_components/`）

先把可行性边界钉死（本轮新核）：

| 事实 | 出处 |
|---|---|
| ASP 确实暴露 `esp_audio_simple_player_register_io()` / `get_pool()` / `set_pipeline()` | `esp_audio_simple_player_advance.h:42, 58, 97` |
| `esp_gmf_pool_register_io()` 把新 IO **插到链表尾部** | `esp_gmf_pool.c:132-146`（`STAILQ_INSERT_TAIL`） |
| `_get_io_item_by_tag()` 从头遍历、返回**第一个**匹配 | `esp_gmf_pool.c:53-65` ⇒ 后注册的同名 `http` 永远命中不了，默认 20 KB 实例优先 |
| `esp_gmf_pool` **没有** unregister / remove IO 的公开 API | `esp_gmf_pool.h` 全量检索无结果 |
| av_processor 未暴露「取 ASP handle」的 getter | `audio_processor.h` 全量检索无结果；业务层只有 opaque `audio_play_handle_t` |
| av_processor 自己已经在用 `register_io` 注册 HLS IO | `audio_processor.c:847-866`（可仿照的调用范式） |

⇒ **§29.3 的结论成立但理由要修正**：不是「没有官方 API」，而是「业务层拿不到 ASP handle + 同名后注册不生效 + pool 无 unregister」。

可选路径（按可追溯性排序）：

1. **正规 fork**：在 `main/idf_component.yml` 用 `override_path` 指向 `components/` 下的受控副本，只覆盖 `HTTP_STREAM_RINGBUFFER_SIZE`。优点：随 git 走、reconfigure 不丢、diff 可查。⚠ **代价（2026-11-11 实测）**：该文件里写死 `manifest_hash`，加一条 override 会触发**整表重解析**，把 17 个组件升了版（button、dl_fft…）⇒ 必须先按当前 lock 把版本钉死再做（`改动记录.md` §30.5）。
2. **ASP `set_pipeline()` + 自定义 tag**：注册一个 `http_big` IO（128 KB），再 `set_pipeline(handle, "http_big", el_names, n)`。⚠ `advance.h:83` 明确写「调用后 `run()` 只运行该 pipeline，**不再按 URI 装配**」⇒ 会破坏 `http` / `file` / `raw` 混用，**不推荐**。
3. **改 av_processor 的 open 阶段**：仿照 `audio_play_register_hls_io()` 在 `esp_audio_simple_player_new()` 之后注册大缓冲 IO —— 仍属改组件，须走路径 1 的 fork 方式。

★ 优先级：**M0（修吞吐）> M1（降字节）> 本条 fork（加缓冲）**。
缓冲是「拿空间换时间」，而当前问题是「时间根本不够」。

### S4 · 网关侧：直接降字节（= §4.0 的 M1，最干净的根治）

把百炼 TTS 的 `format` 从 `wav` 改成 **`mp3` + `bit_rate=48`**（`sample_rate` 保持 24000）：

| | 现在（24k mono WAV） | 改后（24k mono MP3 48k） |
|---|---|---|
| 源码率 | 384 kbps = 48 KB/s | 48 kbps = **6 KB/s** |
| 9.27 s 语音 | 445 KB | **56 KB** |
| 20 KB 缓冲等效 | 0.32 s | **3.3 s** |

优点：**设备端零改动**（`CONFIG_AUDIO_DECODER_MP3_SUPPORT=y`，ASP 自动探测格式；
下游 `rate_cvt(24k→16k)` + `ch_cvt(1→2)` 契约不变），首播更快，VPS 出网流量 ↓8×。

⚠ 与「改成 16000/2ch」那条相反：**不要**改成 16k/2ch WAV（64 KB/s，反而更大）。
⚠ 会改「源格式」，改完必须复验：语速 / 音调正常、`tts stat` 的 `audio` 秒数对得上 `duration_ms`。

### S5 · `task_wdt` 定位（A/B + 打点，不改组件）

1. `idf.py menuconfig` →「音频链路 / Audio Pipeline」→ 取消 `PET_MP_RATE_CVT_ENABLE`，另烧一版跑 S0 场景：
   - watchdog 消失 ⇒ 本地音乐 pool 的 rate_cvt 有关；
   - 仍在 ⇒ 元凶在上行 AFE / recorder 或其它链路（验收清单 J5'）。
   ★ 设 n 时非 44100 歌曲会**建链失败、播不出来**（不是变调），验完改回 y。
2. 定位调用方：开 `CONFIG_ESP_SYSTEM_USE_FRAME_POINTER` 拿完整 backtrace；给 GMF 任务打 tag（av_processor 已有 `esp_gmf_obj_set_tag(work_task, ...)`，`audio_processor.c:1992`）；在 `xz_rec_read_cb` / `xz_play_write_cb` 打印当前任务名 + `uxTaskPriorityGet` + `xPortGetCoreID()`。
3. **不要**直接升 `esp_audio_effects ≥ 1.4.4`：`gmf_audio 1.0.1~1` 锁 `~1.3`、`av_processor 0.7.0` 锁 `^1.3.0`，需连带升 gmf_audio / esp_player / audio_render 一整代（§29.4 ④）。

## 5. 决策树与验收判据

```
烧 M0（BA_WIN=16）+ S0 基线
  ├─ 墙钟/audio 从 ~2.0 降到 ≤1.2、maxgap 百 ms 级  → 吞吐修好了，收工（M2/M1 都不用做）
  ├─ 有改善但仍卡（stalls 高、maxgap 数百 ms）        → 加 M2（fork 128 KB，需先钉版本）
  ├─ 完全没改善、maxgap 仍 1 s 级                     → 查 RSSI / 信道 / 网关出网，转 M1
  ├─ wr_max ≈ maxgap（几十~千 ms）                    → codec / I2S 全双工阻塞 → S2 + 查 DMA
  ├─ task_wdt IDLE1 在 tts=0 时仍报、xrun 涨          → 上行链路占核（R2）→ S2 / S5
  └─ 语速 / 音调异常（慢放）                           → 契约被破坏 → 回查 §1.3 四项
```

| 判据 | 通过线 | 数据来源 |
|---|---|---|
| 下行吞吐 | 墙钟 ÷ `audio` ≤ **1.2**（现在 ~2.0） | `tts stat` |
| TTS 连续 | `stalls ≤ 2` 且 `maxgap < 60 ms` | `tts stat` |
| 写 codec 不阻塞 | `wr_max < 30 ms`、`wr_slow` 不涨 | `xz_play_write_cb` |
| CPU1 不占死 | 串口无 `task_wdt ... IDLE1`；`uplink xrun` 不涨 | `sdkconfig:3176`（5 s） |
| 契约完好 | TTS / 点歌语速正常、双喇叭有声 | 验收清单 J3' |
| 组件零改动 | `git status` 无 `managed_components/`、无 `patches/` | 验收清单 J2'/J6' |
